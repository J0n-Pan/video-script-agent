# 信息流编导工作台（本地部署版）

按《视频号信息流编导脚本编写 Agent 产品需求文档 v1.1》实现，并在 2026-09-20 按第六轮需求扩展。

> 界面名称 2026-09-22 由「视频号信息流编导脚本编写 Agent」统一改为「信息流编导工作台」。
> 名称现由 `src/lib/constants.ts` 的 `APP_NAME` 单点定义（页头 / 登录页 / 标签页 / 导出的 Excel 作者属性）。

两条链路：

1. **脚本还原**（第一~五轮）：把参考视频还原为**可复核、可编辑、可供拍摄团队使用的脚本**；
   **不改写为自有 IP 内容、不润色原话、不提取字幕**。
2. **个性化改写**（第六轮，见第 10 节）：用自有 IP 把同一条内容讲出来——以已复核的参考脚本为**结构骨架**，
   注入 IP 资料包生成多个版本供编导比较选定，再送数字人平台出片。
   这一条是**创作**，与上一条的「一字不改」是两套独立逻辑，互不影响。

**2026-09-21 修复：用户实测「个性化文案生成」时发现的两个问题**（见第 10 节的对应说明）——
① **「保存修改」永远失败**，且因「有未保存改动」连锁导致「选定本版」点不动：
保存接口的路径参数是**候选稿 id**，而详情接口没返回它，界面只好拿 `revisionId` 顶上去 →
服务端按 variantId 查不到 → 400「版本不存在或无权访问」。修法是接口补 `id`、界面改用 `id`
（`baseRevisionId` 仍是修订 id，两者不能混用）。值得记一笔的是**所有服务端断言都是绿的** ——
`verify-rewrite.ts` 直接调函数、参数本来就对，照不到这层接线；因此新增
`npm run verify:rewrite-save`（真实 HTTP + 真实浏览器点按钮，12 项）。
② **数字人「生成数字人视频」报「找不到对应作品记录」，平台上也确实没有记录**：
根因不是平台故障，而是 `AVATAR_ADAPTER` 默认 `mock` 且数字人进程没启动 —— 任务压根没提交，
而界面上的提示语说得像已经提交了；对从未提交的任务点「核对平台记录」又把这个 NOT_FOUND
写成「结果待核对」，把人进一步带偏。现已：任务卡片常显适配器模式与进程存活、
创建提示按适配器分叉、「尚未提交」如实说明并**把脏状态修回排队中**。
③ **顺手补掉一个更贵的洞**：入队这层只按「幂等键」去重，而幂等键是**每次点击**生成的，
所以连点两次会绕过它、留下两条引用同一份正文的在途任务 —— 一旦切到真实适配器就会**重复提交、重复计费**
（「不自动重提」这条红线原本只守在提交环节）。现已在 `createAvatarJob` 增加**同修订在途任务去重**：
第二次点击回放第一条；`FAILED` / `SUCCEEDED` 不算在途（前者允许重试，后者要重出须改稿成新修订）。
④ **数字人任务卡片原先只活在组件内存里**：`avatarJobId` 从未入库也没进详情接口，
点完能看到，**一刷新、一离开页面再回来整块消失** —— 上面 ② 那些「如实说明」等于只在点完那一瞬间可见，
连成品下载链接也一起没了。现在详情接口回填该任务最近一条数字人任务 id
（`latestAvatarJobIdForRewriteJob`），界面按**任务**恢复卡片：换任务时收回、同一任务重进时恢复。
⑤ 顺带修掉三处**界面里把 Markdown 的 `**` 直接当文本渲染**的地方（会显示成字面星号）：
「尚未提交」说明、生成页模型说明、资料包页事实来源说明。

**2026-09-21 真实出片联调：首次真实提交与随之修掉的三处缺陷**（见 10.4）——
按「任务序号 193 → 个性化文案生成 → 第一版 → 选定本版 → 生成数字人视频」在真实账号上跑了一次：
任务建单、界面提示、状态机、卡片的适配器标记都对，**但提交被判成「结果不明」（`AVATAR_SUBMIT_UNCERTAIN`）**，
而平台上其实已经有作品在「创作中」（ID 12847）。三处缺陷：
⑥ **提交成功后读不回作品 ID**：平台点提交会**整页跳转到作品页**，URL 不带 id、响应体也不是 JSON，
   旧逻辑因此把一次已经成功的提交报成「未收到平台作品 ID，结果不明」。
   现在捞不到 ID 时会**按唯一作品名回作品列表确认**（列表里出现自己生成的作品名 = 确定提交成功），
   并顺带把**平台自己的作品 ID**（列表第一列）读回来 —— 探针实测 `td[0]` 就是它。
   Mock 也补了 `[no-id]` 分支复现这个形状，回归断言钉住「不得判成待核对」。
⑦ **「不确定」与「没读回 ID」被混为一谈**：业务层旧写法 `sub.uncertain || !sub.vendorJobId`
   只要没拿到 ID 就进「待核对」。现在只有适配器**查过作品列表也没找到自己作品名**才敢报 uncertain；
   明确已提交的按「平台生成中」推进，后续按作品名查询（不依赖那个 ID）。
⑧ **一个会造成重复计费的漏洞**：提交分支的进入条件是 `!vendorJobId && status ∈ {QUEUED, NEEDS_LOGIN}`。
   如果提交成功却没读回 ID，之后平台会话过期把状态变成「待登录」，下一次轮询就会**再提交一遍**。
   现在改为认 `submittedAt`（在真正点提交前置位）—— 尝试过的任务一律只走查询，绝不回到提交分支。
   同时给 `verify-rewrite` 加了护栏：`AVATAR_ADAPTER` 不是 `mock` 时**直接拒绝运行**（详见第 10 节脚本说明）。

| 12848 | `数字人_20262109 17:10_12565`（账号自测） | 创作完成 | 17:10 → 17:13 |

**账号自己在平台上手动提交也是 2 成 2 败**，所以失败与我们的集成无关。
平台未提供失败原因（悬停状态格无 tooltip、行内无 `title`/`data-*` 属性，「创作参数」弹层只回显参数）；
逐项比对失败件与成功件的创作参数**完全一致**（同一形象、同一音色 `S_N1ptpE2m7`、中文、不显示字幕），
文本内容也与库内 `textSnapshot` 对应（差别只是平台把标点归一成逗号，见第 10 节）。
失败件耗时 12 分钟、成功件 1~3 分钟 —— 像是平台内部多次重试后放弃。故判断为**平台侧间歇性渲染失败**。
平台给出的报错文案是「视频生成失败，请检查配置参数」（泛化的配置类报错，**不是**解码/资源类），
所以「形象视频解码失败」这一猜测可以排除 —— 同样的形象在第二次提交时就成功了。

**第二次提交（同一份稿件 rev2 / 386 字 / 同一形象音色）：全链路成功，拿到成片。**
未做任何参数改动，只重新提交一次：

| 环节 | 结果 |
| --- | --- |
| 平台作品 | `VSA-ov33f3-r2-0921095208`（平台侧 ID **12856**，账面追加 `_12573`） |
| 时间 | 17:52 提交 → 18:03:58 创作完成（**11.3 分钟**，含我方取回共 680s） |
| 成品 | `data/avatars/VSA-ov33f3-r2-0921095208.mp4` — **243.67MB，73.68s，1216×2160，50fps，H.264+AAC，有音轨** |

也就是说：**第一次失败确实是平台间歇性故障**，与形象视频、与文案长度（386 字完全没问题）、与我们的集成都无关。
「把文案切到 150 字」这个方案因此**没有执行**。

同一轮还修掉一处界面污染：取回阶段曾把平台作品行 `innerText` 整行（含作品 ID/名称/分身/端类型/两个时间戳、
带换行与制表符）写进 `reconcileNote`，编导在卡片上看到的是原始表格文本。现在改读**状态单元格**
（`readStatusLabel()`）→ `平台状态：创作中`。

### 4.2 音频识别为何不是 PRD 原定的 `qwen3-asr-flash-filetrans`

PRD 10.5 确认的三模型中，音频识别为 `qwen3-asr-flash-filetrans`。该模型走 DashScope **异步任务**，
`file_urls` 只接受**公网可访问**的 HTTP(S) 地址。本机部署（127.0.0.1）无法提供公网地址，实测结论：

| 尝试的地址 | 结果 |
| --- | --- |
| `oss://dashscope-instant/.../audio.wav`（临时上传凭证上传后） | `InvalidParameter.MalformedURL` |
| `https://dashscope-file-mgr.oss-cn-beijing.aliyuncs.com/...`（同上，私有桶直链） | `InvalidParameter.MalformedURL` |

`dashscope-file-mgr` 临时桶只服务多模态对话类接口，**不是**给录音文件识别用的公网托管。
因此本机部署改走**实时语音识别 WebSocket**：允许直接推送本地音频二进制帧，无需公网地址，且返回句级时间戳。

选型对比（2026-09-12 实测，19.7 秒四句中文，句间 600ms 停顿，真值边界 180/4620、5060/9840、10240/15220、15660/19640 ms）：

| 模型 | 句数 | 时间戳结果 | 结论 |
| --- | --- | --- | --- |
| `paraformer-realtime-v2` | 4 | 与真值边界完全吻合 | **采用** |
| `fun-asr-realtime` | 3 | 第 2、3 句被合并，漏切 | 不采用 |
| `qwen3-asr-flash-realtime` | — | `ModelNotFound` | 不存在 |

推流速率 1x 与 4x 得到**完全相同**的时间戳，故默认 `ASR_PUSH_SPEED=4` 以缩短等待。

另外 `qwen3-asr-flash`（OpenAI 兼容同步接口）虽然支持 Base64 音频、本地可用，但**只返回整段文本、
不含任何时间戳**（annotations 仅有 emotion/language），无法支撑 16 列契约里每段的起止时间，故不采用。

**保留的切换开关**：`.env` 的 `ASR_TRANSPORT=filetrans` 可切回 `qwen3-asr-flash-filetrans`。
若将来具备公网存储能力（如自建 OSS + 签名 URL），改此开关即可，业务代码不动。

### 4.3 填入 `.env`


调参提示：`ASR_MAX_SENTENCE_SILENCE` 偏小会把一句话切碎，偏大会把多句合并；`ASR_DIARIZATION=true`
会额外返回 `speakerId`（不自动等同主体或旁白，PRD 10.6）。

### 4.4 先自检，再切模式

```bash
npm run check:ai                        # 三模型最小调用，产生极少量费用
npm run check:ai -- --audio 你的素材.mp4  # 用真实语音验证句级时间戳与识别效果
npm run check:ai -- --skip-asr           # 只验文本与视觉模型
```

自检直接调用生产适配器（不是另写一份实现），因此「自检通过」等价于「解析进程里的真实调用链路可用」。
它会打印实际生效的区域与域名、密钥掩码、各模型耗时与估算费用，并在失败时给出排查方向。

自检通过后再切模式并**重启解析进程**：

```env
AI_MODE="dashscope"
```

### 4.5 必须重启解析进程

独立进程（`tsx src/worker/index.ts`）不会像 Next.js 那样自动加载 `.env`，
因此项目在 `src/lib/config.ts` 与 `src/lib/db.ts` 顶部显式调用 `loadDotEnv()`（`src/lib/load-env.ts`）。
只重启网页、不重启 `npm run worker`，会出现「网页显示 dashscope、实际仍在跑 mock」的静默不一致。

### 4.6 报价口径

`src/lib/config.ts` 的 `cfg.pricing` 为估算口径，价格核对日 2026-09-12、华北2（北京）档位，**实际以阿里云账单为准**：

| 项 | 单价 |
| --- | --- |
| `paraformer-realtime-v2` | 0.00024 元/秒 |
| `qwen3-vl-plus` | 按单次请求输入 tokens 分档：≤32k 为 1/10，≤128k 为 1.5/15，≤256k 为 3/30（元/百万 tokens，分别对应输入/输出） |
| `qwen-plus` | 输入 0.8、输出 2（元/百万 tokens） |

视觉模型按档位计价而非单一价：不分档会把长输入（9 张采样图可能超过 32k tokens）的费用算低。
每次调用的单价版本随 `ModelUsage.priceVersion` 落库，改价不会改写历史记录。

### 4.7 其他

- 密钥只保存在 `.env`，不下发浏览器、不写入 Excel、不进日志（PRD 11.2）。
- 三类适配器位于 `src/lib/ai/dashscope/`，供应商上传、推流、轮询、错误码与原始返回结构全部收敛在其中；
  业务页面、数据库与 Excel 不依赖供应商返回结构，替换模型不需要改业务代码。

### 4.8 换模型：不用重建 API Key，也不用单独充值

- **API Key 是账号/业务空间级凭证，不绑定模型。** 同一区域内换任何模型都用同一把 key，
  不需要在控制台逐个"开通"，也不产生新费用项。实测一把北京 key 直接调通
  `paraformer-realtime-v2` / `fun-asr-realtime` / `qwen-audio-3.0-asr-flash-streaming` /
  `qwen3-vl-plus` / `qwen3-vl-flash` / `qwen3.8-flash` / `qwen3.8-max` / `qwen3.7-plus` / `qwen3-max`。
- **只有换区域才需要新 key**：北京站与新加坡站密钥互不通用。
- `qwen3-asr-flash-realtime` 官方标注「部署范围：国际」，北京站调用必然 `ModelNotFound`
  （实测 0.4 秒失败）。这**不是**"没开通"，是该区域没有这个模型 —— 换模型前先确认区域部署。
- **充值**：按量付费，全模型共享账户余额，不需要为单个模型充值；
  但**免费额度按模型独立发放**（文本类约 100 万 tokens / 90 天，语音类 36,000 秒），
  换模型相当于换一份新额度，短期内可能反而不用额外充值。
- 换模型的操作只有两步：改 `.env` 里对应变量 → **重启解析进程**（见 4.5）。

### 4.10 换模型时的兼容性注意

- **思考模式默认开启**：`qwen3.8-flash` / `qwen3.8-max` 即使传 `response_format: json_object`
  也默认走思考模式（返回带 `reasoning_tokens`）。实测 9 张图 `qwen3.8-max` 输出 8500 tokens、
  耗时 167 秒、费用 ¥0.40。适配器已显式传 `enable_thinking: false`（PRD 10.5 要求非思考模式）。
- **跨模型族字段名会漂移**：`qwen3-vl-*` 返回 `{"frames":[{"timeMs":…}]}`，
  `qwen3.8-*` 返回 `{"frame_details":[{"time":…}]}`，另有模型直接返回顶层数组。
  视觉适配器现已兼容「顶层数组 / `frames` / `frame_details`」结构、
  `timeMs` / `time_ms` / `time` / `timestamp` 时间字段，以及中文键名回退；
  **返回 0 帧时会抛出明确的 error 级问题**，而不是静默产出空白妆造/场景/情绪。
- **形式建议的键名同样会漂移**：实测 `qwen3-vl-plus` 曾返回
  `videoFormSuggestion/{isMontage,aiGeneratedIntervals}`，而约定键名是 `form/{mixedCut,aiIntervals}`。
  两者语义相反（`isMontage:true` 曾被映射成「混剪」，把真人实拍误判成混剪）。
  现已同时接受两套命名，且**两者都取不到时会给出 `VISION_FORM_CONTRACT_MISSING` 警告**，
  不会再静默退化成一个「看起来正常」的形式结论。
- **调提示词或换模型后，先跑一次 `npm run check:vision`**：它会打印解析后的形式判定与最终结论；
  设 `DASHSCOPE_DUMP_RAW=1` 还会把模型原始返回落盘到 `data/tmp/dashscope-raw/`，
  用于核对「模型实际按什么键名返回」——字段名错配过去是静默发生的，光看日志发现不了。
- **价格分档**：视觉模型按单次请求输入 tokens 分档计价，更换模型后若档位不同，
  需同步更新 `cfg.pricing` 并提升 `priceVersion`，否则费用估算会失真。

## 5 腾讯妙思真实抓取（admuse.qq.com）

### 5.1 已实现的行为

- 完整业务链：链接录入 → **只接受可定位到单条素材的链接**（首页/列表页会被拒绝，不自动批量抓取）→
  登录态检查 → 失败原因准确提示 → **保留原链接** → 本地补传 → 缓存 → 媒体可读性校验 → 只有缓存成功才进入内容解析。
- 真实抓取：复用编导扫码登录一次的**专用会话**，无头打开素材页，三路捕获媒体地址
  （网络响应 / 接口 JSON / 页面 `video` 元素），再用三级下载兜底取回原文件：

  | 级别 | 手段 | 说明 |
  |---|---|---|
  | 1 | 带 cookie 流式直取 | 边下边写盘，不把整片读进内存；HLS 则用内置 ffmpeg 拉流合并 |
  | 2 | 页面自行触发的下载事件 | 少数素材页会自动触发下载，先接住 |
  | 3 | 点页面「下载」入口 + 接收下载事件 | 走浏览器自身登录态与自身下载逻辑，最耐页面改版 |

- 候选地址按证据打分排序并设下限。妙思素材页会同时加载**官网宣传小片与推荐位视频**，
  若「先出现算赢」会静默下错文件 —— 官方首页那几条 `home-v2-cards` 宣传片实测得分 -2 ~ -27，
  未达下限时不会硬下，而是走下载入口兜底或明确报失败。
- 未满足条件时任务会明确提示「抓取未启用 / 未找到登录会话 / 登录态已失效」，并引导本地补传，
  **不会伪装成获取成功**。
- **「抓到了另一条视频」的三道闸门（2026-09-16 修复，务必保留）**。此前出现过
  「粘什么链接都取回一段约 9 秒 / 300KB 的宣传片」：登录态失效时页面被弹回首页并弹出登录框，
  而登录墙正则只收「扫码登录 / 立即登录」这批词，**漏掉了弹窗自己的文案**
  （「微信扫一扫 / 免注册自动登录 / 登录即代表同意」），于是被判为「已登录」，
  接着在页面上挑媒体地址，把登录弹窗的装饰视频 `media/common/login-dialog-deco-video-*.mp4`
  当成了素材本体。现在三道闸门同时生效：

  | 闸门 | 判据 | 拦住的错误 |
  |---|---|---|
  | 登录墙 | `LOGIN_WALL_RE` 覆盖登录弹窗文案 | 不再把未登录判为已登录 |
  | 落点 | `landedReachesMaterial`：最终地址里必须还带着链接中的素材 id | 被弹回首页/别的素材时直接判 `MATERIAL_NOT_REACHED`，页面上的任何媒体地址都不当作结果 |
  | 地址与体积 | `SITE_ASSET_RE`（含 `login-dialog`、`media/common/`）+ `MIN_MEDIA_SCORE` | 站点装饰/宣传素材天然负分，无法通过下限 |

  再加一道**时长校验**：先取原网页标注的素材时长（`insight.durationSec`），
  逐个试下载候选后比对，明显不符就排除、换下一个候选；三级下载兜底产出的文件同样要过这一关。
  这一步专治「详情页同时挂着相关推荐，按地址证据下单却拿到别的视频」。
  拿不到时长判据（网页没给 / ffprobe 读不出）时放行，不否定已下载成功的候选。

  下限取 `MIN_MEDIA_SCORE=20`。**不能调高**：榜单素材本体走无扩展名签名直链，
  实测得分只有 44（无扩展名 6 + `video/mp4` 8 + 体积 ≥2MB 30），
  一度设成 50 导致正常素材全被判为「未发现可下载的媒体地址」。

### 5.2 原网页「视频分析」板块采集（人群分析 / 分镜或高光时序 / 创意标签）

三块内容不在页面 HTML 里，而来自详情接口
`POST /intelligent/api/v1/inspiration/ranking_detail/get`。字段映射（2026-09-15 实测）：

| 导出列 | 接口字段 | 说明 |
|---|---|---|
| 性别特征 | `label_info.core_gender` | 仅取「核心受众」，不并入投放定向倾向 |
| 年龄特征 | `label_info.core_age` | 同上 |
| 分镜/高光 title | `video_script_summary[].phase_name` | 有分镜用分镜阶段名；无分镜时取 `click_time_series` 点击峰值时刻（如 `00:03（点击峰值）`） |
| 创意标签 | `label_info` 其余 20 个键 | 英文键名本地映射为中文（如 `apply_gender` → 定向性别），全部内容拼接 |

**为什么不自己发请求**：妙思接口有 CSRF 校验，必须同时带上 `x-csrf-token`（取自 `csrf-cookie`）、
`x-trace-id`、`x-timestamp` 与前端 SDK 计算的 `x-sign`。实测在页面上下文里用 `fetch`/`XHR`
自行发请求（即使补齐上述全部请求头）一律返回 `{"code":221010,"message":"csrf check invalid"}`。
因此采集改为**收割页面自身已发出的接口响应**（`src/lib/sources/muse-insight.ts` 的
`attachMuseHarvest`，必须在 `page.goto` 之前挂上）：素材详情页渲染时会自行调用该接口，
其响应就含全部板块内容。这样既不依赖签名算法（改版也不易失效），也不额外增加请求。

- 硬限制：板块只对灵感广场榜单内素材提供。接口返回空骨架时，相关字段按需求**标记为空**
  并在「板块说明」里写明原因（区分「不在榜单范围」与「未读到详情数据」）。
- 采集失败不影响取视频：`insight` 为空值并带原因，主链路照常完成。

### 5.3 启用步骤（2026-09-22 起按用户隔离）

### 5.3.1 登录态失效的预警与自查（2026-09-20 修复）

**要解决的问题**：会话过期后，用户仍能提交妙思链接，任务一路跑到 SAVE 阶段才失败 ——
实测 3 次尝试、反复开浏览器、耗时约 14 分钟，最后只看到
「主机视频副本不可用（尚未获取成功或被清理）」，完全看不出真正原因是登录态过期。

**改动**：

1. **登录后自动检查 + 自动弹二维码（2026-09-22 新增）**：每个账号登录工作台后，
   工作台自动检查**该账号自己**的妙思登录态；失效/未登录就直接弹出二维码（可「稍后再说」跳过，
   不阻断本地视频等其它功能）。一次登录只自动弹一次（按浏览器会话 + 按人记忆，登录成功时重置）。
   验收/QA 可在浏览器里置 `localStorage['museAutoLoginDisabled'] = '1'` 关掉自动弹窗
   （否则故意造的「已失效」夹具会真的发起扫码，堵住解析队列最多 10 分钟）。
2. **页头常驻提示栏**：自己的登录态失效时，页头正下方常驻红色提示，写清「妙思链接会在抓取阶段失败，
   脚本文字与来源信息不受影响」，附「去扫码登录」按钮（**人人可点** —— 不再有「统一登录」，
   每个人都给自己扫）。可临时收起；**收起只对当下这一次失效有效** —— 登录态一旦变化
   （修好、或修好后又失效）就重新出现。这一点是验收时发现并修正的：
   早期按「状态值」记收起，导致一次收起后**同名的下一次故障永远不再提醒**。
3. **抓取前置拦截**：`checkAvailability()` 先读**任务归属人**的登录态结论，
   **已确知失效时不再白开一次浏览器**。
4. **登录态探测按成本分三层**，能零成本定罪就不去开浏览器：

| 层级 | 判据 | 成本 |
| --- | --- | --- |
| L0 | 抓取结果本身：成功即有效，`SESSION_EXPIRED` 即失效 | 免费 |
| L1 | 会话文件不存在 / 无 cookie → 必然失效（`MISSING`） | 免费 |
| L1.5 | **会话 cookie 自带的到期时间**：连最晚的一条都已过期即失效 | 免费且精确 |
| L2 | 无头浏览器打开首页读页面文案（`LOGIN_WALL_RE` / `LOGGED_IN_RE`） | 约 4 秒 |

L1.5 是实测发现的关键判据：`state.json` 里 `admuse_token` / `creative_center_token` / `gdt_token`
都带明确到期时间，因此**绝大多数情况下无需开浏览器就能判定过期**，并能在界面上直接显示准确的到期时刻。
取「最晚的一条」而非「最早」是刻意的保守选择 —— 只要还有任一条会话 cookie 未到期，就不敢断言失效，
否则会误拦本来能成功的抓取。

**为什么不做轻量 HTTP 探测**：妙思接口有 CSRF 校验，除 `x-csrf-token` 外还要前端 SDK 现算的 `x-sign`，
即使把头部补全也一律返回 `{"code":221010,"message":"csrf check invalid"}`（见 `muse-insight.ts` 顶部注释）。
所以唯一可信的判据是「真实浏览器渲染后读页面文案」；本项目**不伪造请求**。

**探测时机与节流**：不做定时任务，只在「打开工作台且结论已过期」时探测一次；
结论有效期由 `MUSE_HEALTH_TTL_MS` 控制（默认 15 分钟）。
没有节流的话，在「任务列表 ↔ 导出 ↔ IP 资料包」之间点几下就等于连续触发多次探测。
探测由**解析进程独占执行**（Chromium 单一所有者），web 只读结论文件 ——
web 请求不会被阻塞，Next dev 重启也不会留下孤儿 Chromium。

状态文件（都在 `data/` 下，不入库；**按用户隔离**，`<dir>` = `data/muse-session/users/<userId>`）：
`<dir>/health.json`（结论）、`<dir>/control.json`（web→worker 的单向请求，每人一条）、
`<dir>/login-status.json`（扫码进度）、`<dir>/qr.jpg`（二维码）、
`data/muse-session/login-owner.json`（当前谁占着扫码浏览器，供排队提示）。

**扫码登录的实现要点**（改这块前务必先读 `muse-login-flow.ts` 顶部注释）：

- 二维码在**跨域 iframe** `open.weixin.qq.com/connect/qrconnect?appid=...` 内，
  是一个普通 `<img class="js_qrcode_img" src="/connect/qrcode/<ticket>">`。
  该地址直接 fetch 即返回高清 JPEG（实测 470×470），**不需要 cookie、不需要 Referer**。
- 因此走「取图片地址再自己拉」，**不要**改成元素截图 ——
  实测内层 `img` 元素截图会 30 秒超时；外层 iframe 截图虽可用但清晰度差且带留白。
- **不能**把微信那个 iframe 地址直接嵌进工作台页面让用户扫：那样 cookie 会写进用户自己的浏览器，
  而抓取用的是 Playwright 上下文，`state.json` 拿不到会话，抓取照样失败。
  必须由解析进程在 Playwright 上下文里持有登录，只把二维码**图片**给前端看。
- 登录进行期间不领新任务，保证任一时刻最多一个 Chromium。
- **扫码一次只能一个人（2026-09-22）**：Chromium 只有一个，多人同时请求时
  先来的先扫，其余人的请求留在各自 control.json 里排队，
  界面上会显示「前面 ××× 正在扫码登录，请在队列中稍候」。
- **换微信号必须走「强制登录」**：已登录时导航里没有「登录/注册」入口，点不出二维码，
  流程会（正确地）短路为「无需重新扫码」。因此会话页另给了「更换账号登录」
  （`POST /api/muse/login {action:start, force:true}`），它**不带本地登录态启动**，必然看到登录入口。
  强制登录只在扫码成功后才覆盖会话文件；取消/超时不会动它（验收里专门断言了取消后会话文件 mtime 不变）。
  这个能力同时让「二维码链路」的验收不再依赖「会话恰好过期」这种运行时巧合。

### 5.4 排查命令与端到端验证

```bash
npm run muse:check                                  # 会话是否仍有效（零成本判据优先，必要时才开浏览器）
npm run muse:probe -- "<妙思单条素材链接>"            # 诊断单条素材：登录态、候选地址与得分、截图
npm run muse:probe -- "<链接>" --download            # 再跑一遍正式适配器，验证真实下载
npm run muse:probe -- --nav                          # 导航路由发现，摸清资产/成品库的真实地址
npm run muse:insight -- "<妙思单条素材链接>"          # 只跑「视频分析」板块采集，不下视频、不花模型费
npm run muse:detail -- --scan=10                     # 统计板块有值率（人群/分镜/时序/创意标签）
npm run diag:segment -- --latest                     # 分段链路诊断：识别片段边界 → 模型分段 → 划分结果 → 逐段重复度
npm run diag:segment -- "<本地视频路径>"              # 同上，但直接指定素材文件
npm run backfill:title                               # 回填「原视频标题」：本地导入直接取原文件名
npm run backfill:title -- --fetch                    # 连链接导入一起回填（重开素材页读网页标题，不花模型费）
npm run verify:muse -- "<妙思单条素材链接>"           # 端到端：只给链接 → 真实抓取 → 真实模型 → 两种导出 xlsx（43 项）
npm run verify:muse-session                          # 登录态提示栏 + 会话页 + 接口契约 + 收起语义（39 项）
npm run verify:muse-login                            # 网页扫码链路：二维码取回/取消/不污染状态（19 项）
npm run verify:muse-ttl                              # 探测节流：结论新鲜时不得重复探测（7 项）
```

`verify:muse-session` / `verify:muse-login` / `verify:muse-ttl` 需要**工作台在运行**（web 3939 + 解析进程），
且用**真实浏览器**断言渲染结果 —— 工作台是客户端组件，SSR 只吐加载壳，用 curl 检查会假 PASS。
三者都不需要真实模型，也不消耗妙思额度（`verify:muse-login` 用 `force` 起一次登录、
走到「二维码就绪」即取消，全程不扫码、不动会话文件）。

> 这三个脚本**不假设妙思会话当时是有效还是过期**：`verify:muse-session` 用 `health.json` 夹具
> 强制失效/有效并在退出时还原，`verify:muse-login` 用 `force` 登录绕开「已登录就短路」的分支。
> 依赖运行时真实状态的断言只在「会话恰好过期」时能过，那种脚本不能入库。


`backfill:title` 只回填「原视频标题」这一列（`--fetch` 会重开素材页读网页标题），不触碰任何识别结果。

`diag:segment` 是排查「段落重复 / 首段过长 / 段落时间与内容对不上」的第一手段：它只跑
「语音识别 → 脚本整理 → 划分兜底」三段，把每个原始片段的时间与文本、模型给出的引用、

所以诊断结论可直接外推为正式抓取的行为。保留的截图与 JSON 详情在 `data/tmp/`。

### 5.5 语音识别粒度：长句必须细分（2026-09-16 修复）

**现象**：分出的第一段含一大段文字，且与后面几段大量重合。

**根因**（实测定位，不是分段逻辑的问题）：`paraformer-realtime-v2` 的句切分按静音工作，
而信息流广告多为**连续口播 + BGM**，几乎没有超过阈值的停顿，于是服务端把开头整段并成一句：

| 素材 | 识别片段 | 最长片段 |
|---|---|---|
| 134580000001（69.8s） | 修复前 **2 段** | `0–60.02s`（425 字） |
| 134580000003（70.4s） | 修复前 2 段 | 约 59s |
| 134580000002（123s） | 修复前 4 段 | `2.56–61.96s` |

**对照实验**（确认变量）：推流 1x 与 4x **结果完全一致**（推流速度无关）；
把 `ASR_MAX_SENTENCE_SILENCE` 从 800ms 降到 400ms，片段数 2 → 8，但仍有 37 秒的长片段
（说明该素材确实没有长停顿，调参**不能根治**）。

**修复**：开启 `word_timestamp_enabled`，在**词边界**上按句末标点把长句细分为「语块」，
时间为该语块首末词的真实时间。关键保真依据：**「词文本 + 词标点」拼接与识别原文逐字一致**
（实测 425 字完全一致），拼不回原文时**不切**——宁可粒度粗，也不用错误的切点破坏原文。

效果：同一条素材的识别片段 **2 → 16 个**（最长 9 秒），时间精确到词级。

**妙思标题节点的定位（实测，勿改回旧写法）**：素材详情页没有 `h1/h2`，站点
`document.title` 是「腾讯妙思 - 营销内容AIGC创作平台」，所以旧写法（找 `assetName`/`h1`/`h2`
再退到站点标题）在真实素材上**一律返回 undefined**，表现为标题长期「未提供」。实测确认：
素材标题是页面上**唯一**一个「计算字号 20px + 字重 500 + 内联字体为 PingFangSC」的节点；
同页的指标数字（`4W+`、`1%-3%`、`22.78s`）字号字重相同但字体是 `ODNumber`，必须排除。
`readMaterialTitle()` 按「ellipsis 优先 → 非 ODNumber → 旧选择器 → document.title」的顺序取第一个命中值，
取不到就返回 undefined，**不用站点名冒充**。

> 实现注意：该探测以**字符串形式**传给 `page.evaluate`。本项目用 tsx 运行，函数体内会被注入
> `__name` 辅助变量，在页面上下文里会报 `__name is not defined`。
> 另注意字符串会被 Playwright 当作**表达式**求值 —— 只给一个 `() => {...}` 求出来的函数对象
> 会被序列化成 `undefined`（表现为「Cannot read properties of undefined」），必须写成 **IIFE**
> `(() => {...})()`。两个坑都是实测踩出来的（2026-09-22 在人工接手预填探针上又踩了一次）。

存量记录的「原视频标题」用 `npm run backfill:title` 回填（本地导入直接取 `fileName`；
链接导入需要重新打开素材页，加 `--fetch` 才执行，不调用模型、不产生模型费用）。

### 6.3 原文保真与段落划分兜底（重要）

需求红线是「用转写原文填充，不能对原文作更改」，另一条是「**每段内容不应重复**」。
两条都不能靠提示词约束，必须由程序保证。

**（1）原文由程序回填。** 实测在真实素材（`134580000002`，124 秒）上，整理模型即使被明确要求
「忠实原话」，仍然把 6 段里的 5 段改写/补写。因此流水线在保真校验**之前**执行确定性回填：
`copyText` 一律改为「该段引用的原始语音片段」的原文拼接，模型对文案的改写一律丢弃并留痕。

**（2）段落划分由程序重建。** 实测整理模型会给出**相互重叠的引用**——70 秒素材里第 1 段引用了
横跨 `0–60s` 的整块片段，第 2~5 段又重复引用它。旧实现在「引用的片段已被前段占用」时会
**原样保留模型写的文案**，于是结果就是「第一段一大段文字、后面几段与它大量重合」。

现在由 `partitionSegments()`（`src/lib/validate.ts`）按原始语音片段重建划分，规则：

1. **一个片段只归属一段**：按段落顺序「先引用先归属」，重复引用只记问题、不重复归属；
2. **不丢内容**：模型没引用到的片段，按时间就近归入覆盖它的段落（`UTTERANCE_ASSIGNED` 留痕）；
3. **时间不再信模型**：段落起止由所归属片段的真实时间推导（实测模型给的时间与实际引用范围
   能差 15 秒以上，旧数据里出现过「标称 0–13.9s、内容却到 27.9s」）；
4. **重复段直接丢弃**：一段若没有任何独立片段（内容已全部属于其他段），整段丢弃并留痕，
   绝不留重复文案；
5. 划分后按推导出的真实时间重排，保证段落顺序与原视频一致。

**验收口径**：第 2 段起，每段的「6 字片段与前面段落重合的比例」应 < 50%；
`verify:muse` 会把逐段重合度打印出来并断言。同时「脚本文案 = 各段文案按序拼接」也是一条
不重不漏的强校验（脚本会自动比对）。

处理过程中可能出现的问题码（均为 warn，不阻断出结果）：

| 问题码 | 级别 | 含义 |
|---|---|---|
| `TEXT_REPAIRED` | warn | 模型文案与引用原文不一致，已按原文回填 |
| `DUPLICATE_UTTERANCE` | warn | 片段被重复引用，已按首次归属处理 |
| `UNKNOWN_UTTERANCE_REF` | warn | 引用了不存在的片段 id，已忽略 |
| `UTTERANCE_ASSIGNED` | warn | 有片段未被任何段落引用，已按时间归入相邻段 |
| `SEGMENT_DROPPED` | warn | 该段没有任何独立片段（与前面内容重复），已丢弃 |
| `ORGANIZE_EMPTY` | warn | 模型未返回段落，已按语块逐块保留文案 |
| `ASR_COARSE_SENTENCE` | warn | 有超长识别片段且无词级时间戳，无法细分，需人工核对 |
| `TAG_INVALID` | warn | 标签越界/缺失，已归入「其他」 |

`checkTranscriptFidelity()` 保留为兜底安全网（划分后 `REWRITTEN` / `MISSING_UTTERANCE` 应为 0）。
模型角色因此收敛为：**分段 + 打标签 + 妆造 / 情绪**，不承担文案改写，也不承担「保证不重不漏」。

| 3 | 真人内容占比 ≥ `REAL_PERSON_RATIO_THRESHOLD`（默认 **0.75**），即 AI 占比 ≤ 25% | 真人 |
| 4 | 其余（25%~75% 的中间带） | 其他 |

- 阈值含等号：恰好 75% 归 `AI数字人`，恰好 75% 真人内容归 `真人`。
- 模型无法可靠估计占比时**仍落「其他」**，但**不编造比例**（`ratioEstimated=false`），
  并在依据字段写明「模型无法可靠估计 AI 画面区间」，便于编导识别需复看的记录。
- 原取值 `ai视频` / `有ai片段` / `真人口播` / `真人访谈` / `其他及简短说明` / `待复核` 已全部取消，
  存量记录用 `npm run migrate:form`（先 `--` 试运行，再加 `--apply`）按上表回填。
- 人工纠正入口仍在工作台「任务信息 → 形式」下拉，只提供上述 4 项；
  接口 `/api/videos/[id]/classification` 会对旧取值返回 400。

形式判定为「混剪」时**不再停止解析**：文案照常分段打标签，只是妆造 / 画面场景 / 情绪三项留空
（只标注一次、不做任何推断）。会写入一条 `MIXED_CUT_PARTIAL` 说明供编导知悉。

## 10 个性化文案改写与数字人口播（2026-09-20 第六轮）

### 10.1 要解决的问题与红线

前五轮把参考视频还原成「**别人的**脚本」。这一轮要的是「**用自己的 IP 讲同一条内容**」：

```
参考视频已复核脚本 → 提炼结构骨架（段数 / 顺序 / 六类标签）
                    → 注入 IP 资料包（人设 / 资质 / 方法 / 案例 / 产品权益 / 适用条件）
                    → 生成 3 个版本的自有 IP 口播稿
                    → 编导逐段比较、编辑、选定
                    → 送数字人平台出片
```

**结构由程序裁决，不由模型自由发挥。** 这是本轮最硬的一条红线：生成稿必须与参考段**逐一对应**——

- **段数一致**：参考 7 段就出 7 段。多一段、少一段都判不通过，不自动截断也不自动补。
- **顺序一致**：第 n 段对应参考第 n 段，不许调换（先讲痛点再讲人设 = 废稿）。
- **标签沿用六类且与参考段同标签**：参考段是「干货（解决方案）」，改写段就必须是「干货（解决方案）」。
  模型写出「干货(解决方案)」这种半角括号也认（先归一化回填规范标签并留一条 info 级问题项），
  **不再因此废掉整稿**——这是实测踩到的坑，见 10.2。
- **不补引流结尾**：参考稿没有结尾 CTA，改写稿也不许加。参考段里本来就有行动引导的，沿用其表达，
  但**不新增**、不放大、不改写成更强的催单话术。
- **不增删段内内容**：每段字数应贴近对应参考段（0.7~1.3 倍）。偏离只**提示不拒绝**
  （`REWRITE_SEGMENT_LENGTH_OFF`），因为同一段话可长可短属正常创作，但严重偏离往往意味着模型改了该段的作用。

**与「脚本整理」（F04/F08）是两条互不影响的链路**：

| | 整理（前五轮） | 改写（本轮） |
| --- | --- | --- |
| 性质 | 忠实转写 | 创作 |
| 内容 | 一个字都不能变 | 全换成自有 IP 的说法 |
| 骨架 | 由模型切分，程序保证不重不漏 | 由参考稿固定，程序强制执行 |
| 兜底 | 程序级原文回填（`enforceVerbatimTranscript`） | 程序级结构裁决（`validateRewrite`） |
| 换模型影响 | 只影响本链路 | 只影响本链路，**不重跑 ASR 与画面理解** |

改写**只烧文本 token**，不重跑语音识别与画面理解，所以单次成本约为一次完整视频解析的 1/4~1/3（见 10.2）。

### 10.2 改写模型选型（横向实测，2026-09-20）

| `qwen3.8-flash` | 成功 | 87.6s | 5634 / 3240 | 2114 | ¥0.0133 |
| `qwen3.7-flash` | 3 篇中 **1 篇被废** | 40.4s | 5634 / 3762 | 1881 | ¥0.0124 |

这一轮暴露两个问题，都已修掉：

1. **`qwen3.7-flash` 写的标签是「干货（解决方案)」**——右括号用了半角 `)`。旧逻辑直接判非法、整稿作废。
   已加 `normTag()`：抹平全/半角括号与空格差异后回填规范标签，并留一条 info 级问题项备查，

2. **`qwen3.8-flash` 写太长**（2114 字 vs 参考 483 字，约 4.4 倍），且**在段内自行加了引流引导**。
   参考段没有结尾行动引导，模型自作主张补了一句——正是红线要禁止的。已在硬规则里写死
   「禁止段内新增引流引导」+「每段字数应贴近参考段（0.7~1.3 倍）」，并新增段落长度平衡检查。

**第二轮（v2 规则，`promptVersion=rewrite-v2` / `ruleVersion=rewrite-v2`）**：

| --- | --- | --- | --- | --- | --- |
| `qwen3.8-flash` | 成功 | 66.1s | 5956 / 2454 | **1256** | **¥0.0114** |
| `qwen3.7-flash` | 未再测（标签缺陷已修，验证点在归一化） | — | — | — | — |

| `qwen3.8-max` | 成功 | 48.1s | 5956 / 2689 | 1705 | ¥0.1683 |

缩水到 0.41 倍属可解释的偏离，编导看一眼即可）。

**内容质量核对**（对照资料包 95 条事实逐条追）：flash 与 plus 引用的事实**全部来自资料包**，
无编造。例如 `method-6` / `method-7` 的 cart / scar 编码拆词示例、`credentials` 的证书类资质、
`offer-6` 的「AI APP 15000 词」。`RewriteSegment.factRefs` 可逐段追溯引用了哪几条事实。

### 10.3 IP 资料包（版本化）

资料来自《李威老师9.13日直播话术.docx》，由 `src/lib/rewrite/docx.ts` **零依赖**解析
（`node:zlib` 解 ZIP + 查 EOCD，不引入 mammoth 之类的库），整理成结构化 JSON 落库：

| 键 | 内容 |
| --- | --- |
| `personal` | 人设与经历 |
| `credentials` | 资质证书 |
| `method` | 教学理念与方法演示 |
| `cases` | 学生案例 |
| `audience` | 受众问题 |
| `offer` | 课程与产品权益 |
| `conditions` | 适用条件 |
| `styleSamples` | 风格样例（供模型模仿语气） |
| `boundaries` | **事实边界与禁止表述**（「不得承诺提分」「团体荣誉不得写成个人荣誉」这类，渲染时排最前并宣告为硬约束） |
| `gaps` | **待统一字段与缺失资料**（原文自相冲突的价格/课时/书名/称谓，要求模型不得自行选一条当事实） |
| `facts` | **可引用事实条目**（带 id，`RewriteSegment.factRefs` 按 id 追溯） |

**版本化是硬要求**（「保留后续更新 / 更换新文档的接口」）：

- 导入新文档 = **追加 `v(n+1)` 并把旧版本置为 `SUPERSEDED`**，旧版本不删除、可回看、可重新置为生效。
- **生成任务按版本 ID 锁定输入快照**：已生成的任务永远用当时那一版资料重建输入
  （`rebuildInputFromSnapshot`），**不回读当前生效版本**。所以换了资料包，旧稿仍可复现、可对比。
- 来源文件名与 `sourceSha256` 一并入库，同文档重导入 / 换文档都能识别。

当前库内：**v6（生效）· 212 条事实 · 来源《李威IP形象与文案改写资料初版_v0.1.docx》**。

换版：`npm run rewrite:profile -- "<新文档.docx>" --note "更新说明"`（同文件重导要加 `--force`）；
回看与切换在页面「IP 资料包」（`/settings/ip-profile`）。

**结构化质量体检（`npm run rewrite:profile:check`）**——两个方向一起看，只读、零费用：

| 指标 | 判据 | v6 实测 |
| --- | --- | --- |
| **召回** | 原文里含禁令措辞的句子，其「否定核心」（从「不得/不能/避免…」到句末）是否被资料包任一条目代表 | 35/52（剔除资料自带的操作说明句后 34/44 ≈ 77%） |
| **忠实** | 每个条目的字符 bigram 有多大比例能在原文里找到 | 199/212（94%），**疑似编造 0 条** |

两个反直觉的地方，都写进脚本注释了，免得下次误判：

- **不能用整句算覆盖率**：模型会把长句压成短祈使句（原文「…不能写成所有购买者都会得到的结果」→ 条目「不能写成所有购买者都会得到的结果。」），
  短条目只占长句一小部分，整句判据会把**抽对了的**判成漏抽（同一版资料包：整句 16/52 vs 否定核心 40/52）。
- **召回的分母混着「操作说明」**：《资料初版 v0.1》里既有 IP 事实，也有给 Agent 的操作要求
  （「严格按当前保存的参考视频分段生成」「多版本应在同一结构内比较」）。这类句子含否定词但不是 IP 边界，
  本就不该进事实库（它们由 `rewrite/rules.ts` 承载）。要单看真 IP 边界召回就用
  `--exclude="生成|稿件|多版本|数字人|示例"` 剔掉它们。

资料包结构化本身也踩过三个坑，都留了修复说明：

- **模型把「工作要求」抄进结果**：首版导入 boundaries 20 条里 8 条是提示词自身。现在提示词加了
  「【工作要求】不要输出」+「输出前自检」，并配程序兜底 `stripPromptEcho()`（命中 `归 personal`/`抽进` 等流程用语即剔除）。
- **单次调用抽不全**：10.7k 字资料里 52 句禁令，单次调用无论把条数上限提到多高都只能覆盖 5/7/12 句（20/30/40 上限），
  且同样输入连跑三次结果都不一样 —— 是模型在截断。改为**按 ≤4000 字分块抽取后合并去重**，
  召回与稳定性都明显上升（12 → 35/52）。
- **条目可能是对象**：模型偶尔把一条约束写成 `{字段, 冲突取值}`，`String()` 会变成 `[object Object]` 混进事实库。
  现在按「键值：键值」拍平，拍不出内容就丢弃。

### 10.4 数字人口播（鲲之益平台）

**平台**：鲲之益 AIGC（`aigc.huweilai.cn`，创建页 `/dashboard/to-create-video`、作品管理 `/digital-human/digital-video`），
默认形象 `李威老师_场景1_书房坐姿`、音色 `李威老师`。
**官方 API 尚未确认**，首版用 Playwright 驱动网页，适配器接口已按「日后换官方 API」的形状抽好
（`src/lib/avatar/types.ts` 的 `AvatarAdapter`），换实现只需新增一个 adapter。

关键设计（都有对应验收项）：

| 设计 | 原因 |
| --- | --- |
| **独立 worker + 独立单实例锁**（`data/avatar-worker.lock`） | 数字人出片是长等待（轮询可达 30 分钟），**不能占用全局串行的视频分析队列**（A21）。`npm run worker:avatar` 单独起。 |
| **会话独立于妙思**（`data/avatar-session/state.json`） | 不同站点、不同账号。混用一个会话文件会让两边登录态互相覆盖。 |
| **形象 / 音色必须唯一匹配**，找不到 / 重名 / 资产被移除时明确报错 | 绝不静默换成别的形象或声音（A13）。少一个资产就报错，不猜。 |
| **未选定修订不得提交** | 防止把未经编导确认的稿子直接推给平台（A12）。 |
| **提交结果不明进「待核对」**，核对不重新提交 | 网络超时 / 页面无明确回执时，宁可人工核对，也不重复提交（避免同一稿出两条片）。 |
| **提交后按唯一作品名回列表确认**，不只靠作品 ID | 平台提交成功会整页跳转，URL 不带 id、响应也不是 JSON —— 实测两条快路都捞不到 ID。作品名是自己生成的唯一串，列表里出现它就是**确定提交成功**的铁证；顺带把平台作品 ID（列表第一列）读回来 |
| **已尝试过提交的任务绝不再提交**（认 `submittedAt` 而不是 `vendorJobId`） | 否则「提交成功但没读回 ID」+「会话过期变待登录」两个条件凑齐时，下一轮会**再提交一遍**，同一稿件出两条片、重复计费 |
| **定位作品时 ID 找不到要回退作品名** | 平台作品 ID 是从列表读回来的，读写之间可能对不上；只用 ID 定位会把一条正常生成的任务误判成找不到作品 |
| **作品列表的列按表头定位，不写死 `td[n]`** | 平台加一列就整体错位，而且是**静默取错值**（把「端类型」当状态读出来）。2026-09-22 改为先读表头再定位（`readWorkColumns`），探针在真实列表上验到 8/8 列取对 |
| **「按作品名查不到」不等于「确定没提交」** | 编导在平台上改名后唯一作品名当场失效。2026-09-22 因此把一条**已出片**的任务判成「没提交」并清空了 `submittedAt`。现在必须再加一条「列表里没有本次提交之后新建的作品」才敢下 `cancelled`，可疑就退回「待核对」 |
| **平台作品 ID 是对账的钥匙**（提交瞬间抢读 + 人工可绑定） | ID 不随改名变化、名字会。跳到作品列表那一刻先抢读一行；错过也能用「绑定平台作品」按 ID 接回。**不自动绑定** —— 认错就是把别人的作品当成品交付 |
| **成品下载后持久化 + sha256**，不只依赖平台临时链接 | 平台链接会过期；导出记录与任务解耦（删视频不级联删导出，A22）。 |
| **超平台单次文本上限时提示，不自动拆分、不删减文案** | 自动拆分会产出一条被截断的片子，编导更难发现（§7.3，平台上限尚未核实，先给保守值 5000 字）。 |
| 预览 / 下载走鉴权接口，支持 `Range` | 与视频媒体同样按归属鉴权，不是裸文件路径。 |

**验收走 Mock**：`AVATAR_ADAPTER="mock"`（默认）。Mock 桩按**作品名**内嵌标记触发各分支——
`[needs-login]`（会话失效）、`[uncertain]`（提交结果不明 → 待核对）、
`[no-id]`（**提交成功但读不回作品 ID**，复现真实平台跳转丢参数时的形状，2026-09-21 新增）、
`[fail]`（平台报错）、`[slow]`（长时间生成中，用于验证轮询与超时）、
`[assist-cancel]`（**人工接手未完成提交**：不落任何提交记录，对应真实适配器「查过作品列表也没有」的结论）、
`[assist-uncertain]`（人工接手结束但会话失效 → 待核对）、
`[assist-renamed]`（**提交成功但平台侧被改名**：落一条名字与我们对不上的作品记录，
复现 2026-09-22 事故 —— 按作品名查不到、只有平台作品 ID 认得出 → 待核对 + 可绑定接回）。这样
**在真实账号上很难复现的分支**可以稳定回归，且不花平台额度。

⚠️ **Mock 是默认值，这一点必须在界面上说清（2026-09-21 修复）**：用户点了「生成数字人视频」、
界面提示「后台会提交到平台并等待生成」，于是去鲲之益翻记录 —— 当然没有，因为 `AVATAR_ADAPTER`
默认是 `mock`，压根没提交。现在的做法：

- 任务卡片上常显「**Mock 适配器（不会提交到平台）**」或「真实适配器 · 会话已配置/缺登录会话」；
- 创建成功的提示语按适配器分叉，mock 下明确写「只在本地产出桩成品」；
- 同时显示**数字人解析进程是否在运行**（`data/avatar-worker.lock`）—— 进程没起，
  任务会一直停在「排队中」，这也是「平台没有记录」的另一种成因。

⚠️ **「尚未提交」不得伪装成「结果待核对」（同日修复）**：对从未提交过的任务点
「重新核对平台记录」，平台必然查不到，旧代码把这个 NOT_FOUND 写成「结果待核对 /
Mock：找不到对应作品记录」，把人引向平台排查。现在改成：如实说明「还没提交」、
给出该做什么（启动 `npm run worker:avatar`），并把「从未提交却被标成待核对」的脏状态**修回排队中**。

⚠️ **「提交成功」不等于「读得到平台作品 ID」（2026-09-21 真实提交实测）**：
平台点「生成视频」后**整页跳转到作品页**，URL 上不带 id、响应体也不是 JSON ——
两条快路都捞不到 ID，旧逻辑因此把一次**已经成功**的提交报成「未收到平台作品 ID，结果不明」，
编导以为没提交，其实平台上已经在「创作中」。现在的判定顺序：

1. 先按响应 / URL 捞 ID（窗口 15 秒，实测基本捞不到，别白等）；
2. 捞不到就**按唯一作品名回作品列表确认** —— 列表里出现自己生成的作品名（`VSA-<revId尾6>-r<修订号>-<时间戳>`，
   平台会在后面追加 `_<账号内序号>`，所以用包含匹配）= 确定提交成功，
   顺手把**平台自己的作品 ID**（列表第一列 `td[0]`，纯数字）一并读回来；
3. 只有**作品列表里也确实没有**，才判「结果不明 → 待核对」。

配套的红线：提交分支的进入条件加了 `submittedAt` 判据（见 10.4 的实现要点），
**已尝试过提交的任务绝不再提交一次**。Mock 用 `[no-id]` 标记复现这个形状，回归断言钉住。

⚠️ **任务卡片必须能被重新找回（同日修复）**：`avatarJobId` 原先只存在组件内存里 ——
点完能看到状态与「待核对说明」，**刷新或离开页面再回来整块消失**（成品下载链接也一起没），
用户会以为任务丢了。现在详情接口带回该任务最近一条数字人任务 id
（`src/lib/avatar/service.ts` 的 `latestAvatarJobIdForRewriteJob`），界面按任务恢复卡片：
切到别的改写任务时收回，回到同一任务时恢复。**不会**因为恢复视图而新建或重提任务。

⚠️ **同一修订不得留下两条在途任务（同日修复）**：界面上的幂等键是「每次点击」生成的，
所以连点两次会绕过同键检查、留下两个引用同一修订的排队任务 —— 切到真实适配器后**两条都会被提交、重复计费**
（正是「不自动重提」这条红线想避免的情况，却从入队口漏了进去）。现在 `createAvatarJob`
在「同幂等键回放」之后再加一道**同修订在途去重**（`QUEUED` / `SUBMITTING` / `VENDOR_RUNNING` /
`NEEDS_LOGIN` / `NEEDS_REVIEW` 算在途），第二次点击直接回放第一条。
`FAILED` / `SUCCEEDED` 不算在途：前者要允许编导重试，后者要重出就得改稿成新修订。

#### 提交方式：`auto` 全自动 / `assist` 人工接手（2026-09-22 新增）

`AVATAR_SUBMIT_MODE` 决定「谁来选形象和参数」：

| 模式 | 谁选形象/参数/文件夹 | 谁点「生成视频」 | 适用 |
| --- | --- | --- | --- |
| `auto`（默认） | 适配器 | 适配器 | 无人值守、批量出片 |
| `assist` | **编导**（在真实的平台创建页上） | **编导** | 联调期、平台改版后、需要人工把关参数时 |

**为什么留一条人工接手的路**：自动提交最脆的几段恰好都在「替平台做参数校验」上 —— 形象/音色唯一匹配、
参数滑杆、`成片保存至` 必填文件夹、提交按钮可用性判断。这些选择器平台一改版就崩，而且崩了以后报出来的是
「视频生成失败，请检查配置参数」这种**没人能诊断的泛化错误**（2026-09-21 真实踩到）。
把这些校验交还给平台自己的 UI，比我们猜它的规则可靠 —— 用一点人肉换稳定性。

`assist` 下数字人进程会 `headless: false` 打开创建页，**只预填作品名与文案**，然后停在页面上等：
编导自己挑形象、调参数、点「生成视频」。`auto` 与 `assist` **共用同一套状态机与同一套「按唯一作品名确认」**逻辑，
差别只在提交那一步由谁操作。

三种结局，判据是**两个**（2026-09-22 事故后补的第二个，见下）：

| 结局 | 判据 | 状态 | 可否重新发起 |
| --- | --- | --- | --- |
| 查到作品名 | 列表里有我们那条唯一作品名 | `VENDOR_RUNNING` | — |
| 确实没提交 | ① 作品名查不到 **且** ② 列表里**没有**「本次提交之后新建的作品」 | `ASSIST_CANCELLED`（人工接手已取消） | **可以**，直接再点「生成数字人视频」 |
| 改名嫌疑 | 作品名查不到，**但**列表里有本次提交之后新建的作品（作品名对不上） | `NEEDS_REVIEW`（结果待核对） | 先在工作台「绑定平台作品」把那条作品按平台作品 ID 接回来 |
| 查不了列表 | 会话失效、列表都打不开 | `NEEDS_REVIEW`（结果待核对） | 先 `npm run avatar:login`，再核对 |

⚠️ **`ASSIST_CANCELLED` 敢清 `submittedAt`，`auto` 那条路绝不敢**。清 `submittedAt` 会放开
「不重复提交」的红线，而那条红线是为了防「提交成功却读不回 ID → 会话过期 → 再提一遍」。
这里敢清是因为「查过作品列表、确实没有」是**查询之后的结论**，不是猜的；不清的话编导再点多少次都提交不了 ——
「防重复提交」会反过来堵死正常重来。取消时同时把 `attemptCount` 归零、`reconcileNote` 清空，
并且 `ASSIST_CANCELLED` **不算在途任务**（否则同修订去重会挡住重试）。

⚠️⚠️ 正因为这条路径会清 `submittedAt`，**判据必须保守**。2026-09-22 真实事故：编导在平台上把作品
改成了「信息流编导工作台测试_1」，唯一作品名当场失效 —— 一条**已经出片成功**（平台作品 ID 12857）的任务
被判成「确定没提交」，`submittedAt` 与 `attemptCount` 一起被清掉。丢掉交付 + 放开重复计费，
两个方向都错。所以「作品名查不到」**单独不足以**下 `cancelled`，必须再确认「列表里没有本次提交之后新建的作品」；
时间线可疑一律退回 `NEEDS_REVIEW`（待核对仍算在途，既不重复提交，也留了接回来的路）。

**作品被改名怎么办：`绑定平台作品`（2026-09-22 新增）**

平台**作品 ID 不随改名变化，作品名会**（平台自己也会给名字追加 `_<账号内序号>`）。所以对账的正解是把 ID 拿到手：

1. **提交瞬间抢读**：assist 观察到页面跳到作品列表时，立刻读一行（ID + 名称）——趁编导还没改名，先把这个改名免疫的钥匙存进任务；
2. **改完名也能接回**：卡片上出现「**作品名对不上？**」区块（仅在无平台作品 ID 且无成品时显示），
   可以「从最近作品中点选」（拉平台最近 15 条：ID / 当前名称 / 状态 / 提交时间）或直接手填
   作品 ID / 作品名，点「绑定平台作品」；
3. 服务端 `POST /api/avatar-jobs/[id]/bind` 会**先去平台作品列表核实这条作品真实存在**再写库
   （前端传什么就绑什么不行 —— 一个笔误就会把任务指到别人的作品上），写入后状态回到「平台生成中」，
   数字人进程按 ID 继续跟踪并取回成品；`GET /api/avatar-works` 提供那份最近作品列表。
   **刻意不做自动绑定**：靠「时间线上最近一条」自动认领，万一认错就是把别的作品当成品交付，且错得无声无息。

本次事故即由此恢复：绑定 12857 → 6 分钟内取回 204.7MB 成片（`VSA-4ex88x-r3-0922032404.mp4`，62.1s，含音轨）。

配套的**列定位改造**：作品列表的列原先写死下标（ID=0 / 名称=1 / 状态=5 / 提交时间=6），
平台**加一列就整体错位**、而且是静默取错值（比如把「端类型」当状态读出来）。现在先读表头再定位
（`readWorkColumns`），只读探针 `_scratch/probe-adapter-works.ts` 在真实列表上验到 **8/8 列全部取对**。

界面与状态处理配套（都有回归断言）：

- 卡片增「**人工接手模式（形象与参数由你选）**」标记，创建成功提示改为「请在弹出的浏览器窗口里选好形象与参数，自己点生成视频」；
- 状态 chip 显示「人工接手已取消」，横幅给出**确定结论 + 出路**（没有提交、不产生费用、可直接重新发起），
  并附上取消原因（关闭窗口 / 超时）；
- **「已取消」不得复用「尚未提交（排队中）」那块提示**：两者都是「无平台 ID + 提交次数 0」，
  但结论相反 —— 前者该去重新发起，后者该去查数字人进程。判据相同、文案必须分叉（`verify-avatar-card` 钉住）；
- 「重新核对平台记录」在已取消时**禁用**，服务端也会直接回「未提交、无需核对」，
  不去查平台、更不会把已取消翻成「待核对」；
- 注意窗口开在**运行数字人进程的那台机器**的桌面上（单机部署即本机）。

#### 真实账号联调结论（2026-09-20，已按真实 DOM 校正）

会话已用真实账号扫码打通，页面结构经 4 轮探针核对，`SELECTORS` 与交互顺序按实测重写。
**「点击提交」尚未真实跑过**（会消耗平台额度，需确认后再做），但提交前的全部步骤已用
`npm run avatar:smoke` 在真实账号上验证通过。

| 探针核实的事实 | 对实现的影响 |
| --- | --- |
| 登录凭据是 **`localStorage.token`**，不是 cookie | 会话检测不能只看 cookie，否则会假报「会话可用」（`avatar:login --check` 踩过）；现在以 token 存在性为硬信号 |
| 形象列表是左侧**平铺卡片** `div.list > div.item > div.name`（不是按钮、不是弹层） | 按名字节点精确计数；选完还要读「当前形象：<名字>」回显确认，不假设点选生效 |
| 音色入口是 `div.choose-btn.choose-voice-btn`（**是 div 不是 button**，`button:has-text` 命中 0） | 选择器改成 CSS + 文案双候选；弹层是 Arco Modal（标题「发音人」），**必须点弹层内的「确定」**（Escape 关不掉）；全局找「确定」会点到别的弹层 |
| 页面里同时挂着多个 `div.arco-modal`（隐藏的排在前） | 弹层定位**必须带 `:visible`**，否则 `.first()` 稳定取到隐藏那个，永远判「没弹出」 |
| 参数标签在 `div.slider-item > div.label`（口播语速 / 口播音量） | 按 label 文案定位参数行，找不到就不动（默认值本就是 1.0） |
| **「成片保存至」文件夹是提交前必填项** | 形象/音色/文本/作品名全填好后「生成视频」**仍然 disabled**，唯一空着的就是它。现已按 `AVATAR_SAVE_FOLDER` 选择（默认「李威数字人」），选不到就报错、绝不随便挑一个（会把成片存进别人目录） |
| 该控件选中后**搜索 input 会从 DOM 消失**，选中值在 `div.save-directory span.arco-select-view-value` / `title` | 回读不能读 input 的 value（永远空）；以 `div.save-directory` 为锚点读 value 节点 |
| 作品名输入框 placeholder 是**「请输入视频名称」** | 原候选靠泛化的「名称」侥幸命中，而「成片保存至」的搜索框也含「名称」——已改为显式匹配，避免把作品名填进文件夹搜索框 |
| 作品列表是真 `tr.arco-table-tr`；状态文案「创作中 / 创作完成 / 创作失败」 | 状态映射按其实际文案，且**先判「创作中」**再判完成，否则进行中会被 `/完成/` 误判成成功 |
| **成品 mp4 在阿里云 OSS**（`kzyszross.oss-cn-beijing.aliyuncs.com`），不在站点主域 | 原白名单只有 `aigc.huweilai.cn`，成品链接会被 `AVATAR_URL_HOST_REJECTED` 直接拒掉。现按云存储后缀（`.aliyuncs.com` 等）默认放行，并能报出「平台换了存储域名」的提示 |
| 成品地址要**点行内「播放视频」**才出现在 `<video src>`；封面列只是 `?x-oss-process=video/snapshot` 的 jpg | 取成品走「先找行内直链 → 再点播放器读 `<video src>`」两级 |

两个实现上的安全选择（都会影响「会不会误报」）：

- **不点禁用按钮**：旧实现直接 click 再等 60s，会报「已提交但拿不到 ID，进入待核对」——
  而其实什么都没提交。现在等按钮可用才点；等不到就报 `AVATAR_SUBMIT_DISABLED` 并指出页面提示缺什么。
- **截图必须 await**：旧写法 `page.screenshot().catch()` 没有 await，`finally` 一关浏览器就一张没落盘，
  而截图恰恰是判断「平台页面到底变成什么样」的唯一线索。

**导出新增第三种**：`EXPORT_KIND=REWRITE`「信息流改写稿」，一个任务一张表，
列 `稿件版本 / 序号 / 标签 / 正文 / 预计口播时长（估算）`。
「预计口播时长」用「**约 X 秒**」表达——它是按字速估算的，**不是时间码**，

## 11 已知限制与说明

- 妙思真实抓取已启用并验证通过（见第 5 节）；三模型真实调用已跑通（见第 8 节）。

- 音频识别为**实时推流**，处理耗时与音频时长同阶（当前 4x 倍速下约 0.25~0.9 倍）。
  长素材的等待时间明显长于异步批处理，`STAGE_TIMEOUT_MS` 已按上限 30 分钟素材放宽到 15 分钟。

  此时性别/年龄/分镜/创意标签按需求标记为空并写明原因，不是抓取故障；
  也无法通过自行发请求绕过（妙思接口有 CSRF 校验，详见 5.2 节）。
- 六类标签的**分段边界由整理模型决定**，同一素材两次运行的分段数与标签分布可能不同（无随机种子）；
  但「不重不漏」由程序保证，不受模型随机性影响（见 6.3）。
  文案本身由于程序级原文回填始终与转写原文一致，但「一段一个标签」的归类质量仍需编导在复核界面确认。
- Mock 模式下的指纹不进入判分：验收用的素材是 `ffmpeg` 生成的合成画面与正弦音轨，只验证流程与格式，不用于评估识别质量。
- `data/` 目录（数据库、媒体缓存、画面取样帧、导出）默认保留至用户删除，删除视频会同步清理其版本、取样帧、媒体与相关合并导出文件。

第六轮（改写 + 数字人）专项说明：

- **改写是创作，不是转写**：`ScriptRevision` 的原文保真保证（一个字不改）**只适用于脚本还原链路**，
  改写稿（`RewriteSegment`）内容与参考段完全不同是**预期行为**，不要拿原文保真校验去卡改写稿；
  改写稿的约束是「结构一致」，由 `src/lib/rewrite/validate.ts` 单独裁决。
- **改写仍受模型随机性影响**：多版本之间、两次运行之间，表达与分段长度会有差异（`temperature=0.85`）。
  结构不变由程序保证，但**哪一版更好仍需编导判断**——三版并列展示就是为了这个。
- **改写模型选型尚未最终确认**（推荐 `qwen3.8-flash`，见 10.2）。改 `REWRITE_MODEL` 需要**重启 worker**，
  且费用估算会按新模型名自动取档（`pricing.rewriteModels`）。
- **数字人平台是第三方网页，不是稳定 API**：官方 API 未确认，当前 Playwright 适配器依赖页面结构，
  平台改版会导致选择器失效（失败时每步留截图便于定位，见 10.4）。真实账号上**已联调并拿到成片**
  （2026-09-21）；平台一改版就崩的那几段参数选择器已有 `AVATAR_SUBMIT_MODE=assist` 兜底
  （形象与参数交给平台自己的 UI 和编导，我方只预填作品名与文案）。
- **数字人平台单次文本上限尚未核实**（先给保守值 5000 字）。超限时只提示、不自动拆分、不删减文案。
- **IP 资料包内容是业务资料，不进版本控制**：`data/` 已整体忽略；仓库内不含资料原文。
  资料包的版本化只解决「换文档」的可追溯性，**不解决内容准确性**——引用是否有夸大，仍需编导在上线前核。
- 数字人成品落 `data/avatars/`，与视频媒体同样默认保留至用户删除。
- **改写生成在 HTTP 请求内同步完成**（3 篇约 35~90 秒），期间页面要一直开着。本地部署无网关超时，所以够用；
  但**请求被中途打断（关标签页 / 杀进程）时，该任务会停在 `RUNNING`**——没有像视频解析那样的断点恢复机制。
  页面会把它标成「已中断 / 可能已中断」并给出重新生成入口（不会假装还在跑），重新生成一次即可。
  后台进程存活时即便关掉标签页，请求通常仍会跑完（Node 不会因为客户端断开而撤销进行中的 Promise）。
  若日后要上服务器或加大版本数，应改为「入队 + worker 推进」。
- **改写稿的「预计口播时长」是估算值**（按字速折算），不是真实时间码；数字人实际出片时长以平台为准。
- 改写稿导出**不含参考视频的原始时间码**：改写后文案长度已变，套用原片时间码会误导拍摄团队。
